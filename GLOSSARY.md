# Glossary

PrajnaTrade is a single-context repository. These terms are used in issue titles,
tests, CLI output and the ADRs; prefer them over synonyms.

| Term | Meaning |
| --- | --- |
| **Sealed snapshot** | A content-addressed set of inputs sealed outside Git. The snapshot ID hashes the canonical manifest, including the three partition fingerprints; a payload is verified against its descriptor before use. |
| **Partition** | One frozen, fingerprinted range of a sealed snapshot: `discovery`, `validation`, or `final_holdout`. The split is `floor(3N/5)`, `floor(N/5)`, remainder. The #50 70/30 research split subdivides only the existing Discovery interval; it never changes these sealed partitions. |
| **Discovery / Validation / Final Holdout** | Discovery informs initial strategy development. Validation supplies reusable evidence for revision and selection under a budget. Final Holdout provides a controlled independent test of a frozen selection. |
| **Research partition protocol** | The round's frozen rule for how the Campaign's Discovery interval is partitioned and scored: `discovery_replay` (protocol v1, the #43 replay of the whole frozen Discovery interval) or `trailing_validation` (protocol v2, the leading-development split with formal trailing-segment Validation). The protocol is recorded in the round kickoff and every locked version; readers default a missing protocol to v1, and old rounds, receipts and campaigns keep their recorded protocol. |
| **Development segment / Trailing segment** | The two contiguous, disjoint, exhaustive slices of a Campaign's sealed Discovery interval under protocol v2: `development_sessions = floor(N * 70 / 100)` and the remainder trailing. The frozen descriptor records each segment's dates, session count and content hash plus a canonical `split_hash`. The Campaign copy and every Discovery experiment hold only the development segment; the trailing segment is reserved for formal Validation. |
| **Research direction** | A strategy design with a stable identity across names, revisions and Campaigns. The research lead declares whether prior Holdout feedback influenced the design. |
| **Research round** | A Campaign within a direction with a confirmed objective, constraints, comparison protocol and Validation budget. It ends in selection or a retrospective. |
| **Research Loop** | The round → submission → Validation → detail/feedback → review-decision loop (issues #43/#50) over one Campaign: an approved round contract, content-addressed locked versions with optional revision/feedback provenance links, a Discovery-evidence replay (protocol v1) or formal trailing-segment Validation (protocol v2), controlled question-based detail over the published receipt, recorded feedback, cross-round reuse disclosure and exactly one current human review state per version, built from immutable decisions. It never reads a protected partition or spends a protected allowance. |
| **Lightweight Validation** | The protocol-v1 trusted replay of a locked version and its benchmark over the frozen Discovery interval (`round validate`). It reuses that interval's evidence and the frozen scoring start, execution rules and costs; its verdict is `passed`, `failed` or `insufficient_evidence`, and it neither opens a protected partition nor writes a query debit. `round revalidate` records a new evidence epoch after a data or platform fix while keeping the strategy identity; on a corrected successor snapshot it recomputes the affected Discovery evidence and records the original and recomputed runs plus the affected diff. |
| **Formal trailing Validation** | The protocol-v2 `round validate` entry (#50): it scores a locked version and the equal-weight benchmark on the **trailing segment only**, from that segment's first session with the same initial cash, costs and execution rules, using the sealed Discovery payload's development segment (plus any sealed prior history) as prehistory. It is distinguishable from #37 protected Validation and from the v1 Discovery replay by `validation_kind: trailing_validation` and its protocol/segment fields. Like v1 it reads only the sealed Discovery payload, never a protected partition, and never writes a query debit. |
| **Validation detail query** | The agent-and-operator `round detail` command over a version's **published** project receipt (protocol v2 or legacy): it records a non-empty question plus a fixed allowlist of receipt records (`summary`, `metrics.*`, `checks.<group>`, `runs.*`, `fills.*`, `observation`, `protocol`, `provenance`, `usage`, `development`, `trailing`, `scoring`, `warmup`, and `replay` for a legacy receipt) into a content-addressed `detail_access_id` and returns only those blocks. It never projects the trusted-only `curves`, never reads a sealed payload or ledger, never consumes a Validation use or admission, and identical requests replay the stored resolution. `round status` lists each version's recorded questions without duplicating the answers. |
| **Validation feedback / revision link** | The agent-and-operator `round feedback` record that links a version's terminal Validation receipt (optionally one of its detail accesses) to the impact it had and to the next known experiment in the Campaign; it is content-addressed, never consumes a use, and is exposed per version by `round status`. A later `round submit` may cite a prior version (`revision_of`) and prior-version feedback (`feedback_ids`): both are validated provenance stored in the submission body but deliberately excluded from `version_id`. |
| **Reuse disclosure** | The v2 `round open` record of previously used evidence on the same snapshot: for every earlier round in the same project whose Campaign used the same `snapshot_id`, its protocol and the interval its published receipt actually used (formal `trailing`, or the legacy replay's scoring interval), the intersection with the new round's trailing segment, and the earlier rounds' feedback rows. It is computed once, stored outside `kickoff_hash` in the trusted round record and project copy, returned unchanged on replay (including across the trusted-write crash window), and absent for protocol v1 rounds; old receipts keep being read under their original protocol. |
| **Automatic Validation limit / Validation use record** | The protocol-v2 round's frozen number of automatic distinct-version trailing reads (`validation_policy.auto_validation_limit` in the kickoff). The first counted read of a version atomically reserves one immutable `research_loop_validation_uses` row (`kind: "automatic"` or `"manual"`); a resume, replay, receipt view or revalidation of the same version never consumes again. Known-gap pre-checks reserve nothing, while interrupted, failed and insufficient reads keep their row. `round status.validation_allowance` reports the counters (`auto_limit`, `automatic_used`, `manual_used`, `total_used`, automatic `remaining`) and use rows; an admission grant is not a use and writes no row. |
| **Manual Validation admission** | The operator's write-once, content-addressed grant of one extra trailing read to one locked version after (or while) the automatic Validation limit applies (`round admit`, protocol v2 only). It records the reviewer, reason, and how the next comparison changes the choice (`comparison`, `selection_impact`) in `research-loop-admissions/<admission_id>.json` plus a project row; `admission_id` addresses the immutable body and `granted_at` is stored alongside. One admission binds one version, identical content replays, and a different admission for that version is `ADMISSION_CONFLICT`. Granting is not a read and changes no counter. The admitted version's next `round validate` consumes it atomically as one `manual` use row with the `admission_id` and a `manual` receipt `usage`; no other version can consume it, and replay/resume never consumes it twice. |
| **Selection-basis traceability** | The chain an operator can follow from `round status` plus one `round detail` with `records: ["provenance"]` without re-reading sealed data: snapshot → round → version → experiment → locked protocol → actual development and scoring dates → warmup source → usage/allowance (automatic or manual admission) → feedback → review state → tracking. The synthetic CLI test proves the mechanism for #35; a real receipt and real forward acceptance remain #35's gate. |
| **Round lifecycle** | The research-visible state of a research round: `research` (open, and for protocol v2 with automatic slots left), `awaiting_validation_admission` (open v2 with `automatic_used >= auto_limit`, whether or not a manual admission was granted) or `converged` (closed). It never replaces the stored `status: open|closed`; the automatic-limit pause and a closed round are distinct states, and Discovery experiments stay allowed while validation waits. |
| **Review decision / review state** | `approve`, `return` or `end`, recorded as an immutable content-addressed decision by a named reviewer with a reason. A version has exactly one current review state (`pending`, `approved`, `returned`, `ended`); `ended` is terminal and `returned` may later be approved or ended. A passed Validation never pre-fills the decision. |
| **Campaign** | A bounded, frozen research run over the Discovery partition with a fixed provider, config, seed and budget. It owns attempts, experiment receipts and budget accounting. |
| **Experiment** | One submitted attempt inside a campaign, with a hypothesis, strategy/parameters and a receipt-driven result. Parent/child experiment IDs record iteration; resubmission is idempotent. |
| **Candidate** | A frozen experiment selected for Final Holdout. Its selection links the strategy version, the precise Validation evidence, the reasons for selection and the remaining risks. |
| **Protected evaluation** | A trusted Validation or Final Holdout run under a fixed protocol that records authorization, the exact range, isolation evidence, an allowance debit and the scored result. |
| **Query debit** | The allowance charged before a sealed read. Each new version uses one Validation allowance in its round. A direction uses one Holdout opportunity for an interval. The allowance is scoped to the protected direction-bound flow: lightweight Validation reuses Discovery evidence and spends none, and the #43 manual simulated-tracking admission has no protected debit. The legacy debit represented a whole partition. |
| **Holdout authorization** | The research lead's approval to evaluate the exact frozen selection and enable that release on a trusted pass. It records the range, the comparison evidence, and the lead's selection independence declaration. |
| **Controlled report** | The operator-only report rendered from stored immutable evaluation records (`evaluation report`). It shows the exact plan, linked authorizations and debits, coverage, thresholds, costs, neighbourhood, regimes, curves and evidence verdict. |
| **Immutable release** | The unique version of a frozen Candidate backed by successful evidence and human approval. A trusted Holdout pass can fulfil conditional approval and schedule its enablement. |
| **Shadow Live** | The trusted forward-accounting ledger for released versions (`shadow update`). Each version has an independent cash/position/order account; one trading day commits atomically in SQLite, reruns return the stored day, and no order is filled retroactively. The Evidence Loop reuses this same ledger and engine, but its versions are admitted by a manual simulated-tracking review decision, not by a protected `release approve`/`enable` or a Holdout authorization. |
| **Evidence Loop** | The observation and accounting loop for an approved simulated-tracking version (issue #43): Shadow Live records due/filled/unfilled tracking opportunities, a data-derived observation term confirmed by the researcher, scoped pauses and a human continue/pause/retire review. It reuses the Shadow Live ledger; it is not protected evaluation, and a synthetic ledger is not forward evidence. |
| **Simulated tracking** | A manual admission mode for #43: a human review decision creates a write-once `manual_tracking` artifact and exactly one `enable` event at the first eligible trading session, and Shadow Live accounts the version from then on. It is not a conditional release, implies no protected evaluation, and never sends a real order. |
| **Observation recommendation** | The platform's proposed observation term computed from the candidate replay's rebalance cadence (`recommended_sessions` with a `basis` record), which the researcher confirms or adjusts in the approval input. Reaching the term with too few due opportunities extends observation rather than ending it. |
| **Tracking opportunity** | One committed Shadow Live decision point where the strategy's normalized target weights changed. Due, filled and unfilled orders are recorded separately; a drift-only reorder under an unchanged target is not an opportunity, and intent without a fill still counts as due and contributes to the observation review. |
| **Pause scope** | The recorded range of a pause: the affected version (default) and the data/execution/ledger processing that was distorted. A scoped pause stops only that version's new signals; other versions keep committing, and pending orders and valuation continue. |
| **Correction disposition** | The trusted re-review of a verified dividend-correction revision against a release (`release disposition`). It records exposure by snapshot lineage plus evaluated ex-date range, classifies `sustained` / `pending_review` / `no_longer_supported`, may pause new signals at the first uncommitted after-close point, and never opens a sealed payload or debits a query. |
| **Scenario status** | In the six-scenario acceptance manifest: `verified`, `blocked`, `failed` or `not_run`, always scoped by data/agent/period. Synthetic evidence verifies only its synthetic scope and never satisfies the real-chain gate. |
