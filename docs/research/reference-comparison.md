## 1. karpathy/autoresearch (Spec §3.1: "primary architecture reference")

Sources: [README.md](https://raw.githubusercontent.com/karpathy/autoresearch/master/README.md), [program.md](https://raw.githubusercontent.com/karpathy/autoresearch/master/program.md). Also inspected (completion pass, via `gh api`, key lines only — grep of constants/function/class names and exit paths, not a line-by-line read): `prepare.py`, `train.py` at `https://github.com/karpathy/autoresearch/blob/master/<file>`. README and program.md read to ~7,000 chars each.
- `prepare.py` fixes `MAX_SEQ_LEN = 2048`, `TIME_BUDGET = 300`, `EVAL_TOKENS = 40 * 524288`, `VOCAB_SIZE = 8192` under "Constants (fixed, do not modify)" (lines 26-45), and **pins one validation shard** (`VAL_SHARD = MAX_SHARD`, lines 43-44); training iteration excludes it (`_document_batches`, lines 254-263).
- `train.py` imports `TIME_BUDGET`, `evaluate_bpb` from `prepare` (line 26), stops training when `total_training_time >= TIME_BUDGET` (line 603), aborts with `exit(1)` if loss is NaN or >100 (lines 570-572), then calls `evaluate_bpb` and prints `val_bpb`, `peak_vram_mb` (lines 613-625). So the fixed evaluator and the fast-fail on divergence are in code, not only in prompts.

- Three files matter: read-only `prepare.py` (data, evaluation), agent-edited `train.py`, human-edited `program.md` (README "How it works").
- Fixed 5-min budget, one metric `val_bpb` → comparable experiments (README "Design choices").
- Loop: commit idea → run → grep metric → advance branch if better, `git reset` otherwise; crash = log and move on; >10 min = kill; baseline first; "NEVER STOP"; `results.tsv` (commit, metric, memory, keep/discard/crash, description) untracked (program.md "The experiment loop", "Logging results").
- Agent may not edit the evaluation harness or add dependencies; simplicity criterion (program.md "What you CAN/CANNOT do").
- Fit to Spec: matches §6.5/§7 (edit strategy code, run, keep/rollback). Gap (narrowed to what the code shows): the pinned validation shard is a fixed held-out *eval set*, but the agent sees its `val_bpb` on every iteration and selects on it — there is no second, locked final test and no trial-count/multiple-testing accounting in `prepare.py`/`train.py`/`program.md`; isolation is by instruction ("Do not modify `prepare.py`"), not enforced in the code I inspected. Spec §8/§9 need AQR-style additions.

## 2. AQR — experiment/validation behaviour

Read in full or substantially: [README.md](https://raw.githubusercontent.com/henryzhangpku/autonomous-quant-researcher/main/README.md), [program.md](https://raw.githubusercontent.com/henryzhangpku/autonomous-quant-researcher/main/program.md), `docs/AUTONOMOUS_QUANT_RESEARCH.md` (full), `research/control/{LOOP.md,gate.yaml}` (full), `research/autoresearch.py` (lines 1-150), `research/v3/evaluator.py` (lines 1-330 of 17 KB-file), `research/v3/ledger.py` (1-90), `research/v3/stage_store.py` (1-60), `research/v3/program.py` (1-80). Base: `https://github.com/henryzhangpku/autonomous-quant-researcher/blob/main/<path>`. The README itself says it is a reference implementation and the production engine is private.

**Two candidate models coexist (important):**
- v3 mission: model returns strict JSON `{hypothesis, rationale}` from a bounded vocabulary; "does not write Python" (`docs/AUTONOMOUS_QUANT_RESEARCH.md` "Declarative hypothesis boundary").
- Generic `program.md`/`LOOP.md`: "maker proposes candidate code", returned as JSON with `code` and `rationale`, edited only under `.research/runs/*/candidates/**` (`program.md` "Loop"; `research/control/gate.yaml` `candidate_allow/deny`).
- Spec §6.2/§6.5 requires Agent-written Python strategies, so PrajnaTrade follows the code-candidate model and **cannot** rely on AQR's "nothing to sandbox" argument (README "Why a finance loop…" item 1). Spec §9 correctly says subprocess ≠ sandbox. `gate.yaml` declares `forbidden_imports`/`forbidden_capabilities` (e.g. `socket`, `subprocess`, `network_access`). Enforcement code now inspected in `research/lab/loop.py` (base `https://github.com/henryzhangpku/autonomous-quant-researcher/blob/main/`):
  - Static AST screen `_validate_candidate_source` (lines 1007-1064): only `math`/`statistics` imports plus an allow-list of `research.backtest` structure factories; bans calls/names `eval, exec, open, getattr, __import__, compile, globals…` (`FORBIDDEN_CANDIDATE_CALLS`, lines ~59-72) and any private (`_x`) name/attribute.
  - Execution: `subprocess.run` of the fixed validator with `cwd=workspace_dir`, timeout from policy, and an env stripped of `OPENAI_API_KEY`, `AUTOQUANT_LAB_API_KEY`, broker-prefixed vars (`_run_validator` 660-679, `_candidate_env` 731-749).
  - `research/autoresearch.py` checks mutable-path compliance *after* the run, from `git status` before/after (`run_once`, `_git_changes`, `_is_allowed`) and records `boundary_violations`; it detects, not prevents.
  - Interpretation (mine): this is a denylist/AST filter plus env scrubbing and a subprocess, not OS-level file/process/resource isolation — consistent with Spec §9's warning. I found no seccomp/container/rlimit code in the files read. Also note the allow-list excludes numpy/pandas, which an ETF strategy would need; PrajnaTrade must define its own allowed-import policy.

**Validation mechanics (cite → PrajnaTrade analogue):**
- Immutable chronological stores: discovery 2016-2021, validation 2022-2024, holdout 2025+; each store content- and manifest-hashed, tampering fails closed (`docs/AUTONOMOUS_QUANT_RESEARCH.md` "Staged evidence lifecycle"; `research/v3/stage_store.py` `StageManifest`, `materialize_stage_stores` "refuse to replace existing evidence"; `research/v3/program.py` `SPY_PRICE_V3.stage_dates`). → Spec §8.
- Shortlist ≤3 frozen and hashed after discovery; validation sees only that set; alpha = 0.05/shortlist size (Bonferroni) (design doc "Admission, diversity, and shortlist rules"; `evaluator.py` `alpha = 0.05 / shortlist_size if stage == Stage.VALIDATION`). → Spec §7 `max_finalists: 3`, §8 multiple testing.
- Holdout opens only after a durable receipt; a failure after the receipt still consumes it. Code-verified in `research/v3/campaign.py`: state machine requires `holdout_receipt` from `holdout_ready` only (lines 58-69); `run_holdout` (923-972) takes an interprocess lock, raises `HoldoutConsumedError` if a receipt exists, appends the `holdout_receipt` event, and only *then* calls `_stage_access_factory("holdout")` and the evaluation callback; an exception appends `holdout_failed` and re-raises (no retry). Events are an append-only hash-chained `events.jsonl` replayed on every open, with contiguous-sequence, hash-chain, integrity-hash and idempotency-key checks (lines 520-541); `state.json` is a rebuilt view (line 3-4).
- **Narrowed claim:** I found no human-confirmation prompt in `run_holdout`; "explicit human action" is a deployment/design property (design doc: "requires a deliberate user action"), i.e. the method must be called by a caller. PrajnaTrade must implement its own confirmation (e.g. a required CLI flag/typed phrase) — Spec §8.
- Gates (all must pass): positive edge after base costs, positive base-cost net mean, positive weekly-cluster bootstrap lower bound (2,000 deterministic resamples), positive elevated-cost mean (1.5× cost), finite metrics, sample floors (120/60/30 trades; 40/24/12 weeks) and per-year floors in validation; ranking score only orders gate-passers (design doc "Modeled evaluator gates"; `evaluator.py` constants `BASE_COST_FRACTION=0.03`, `ELEVATED_COST_FRACTION=0.045`, `BOOTSTRAP_RESAMPLES=2_000`, `STAGE_FLOORS`). → Spec §8 cost sensitivity / regime-year checks. Note the floors are for SPY options trades and **do not transfer**: a daily five-ETF allocation has far fewer "trades"; thresholds must be re-derived.
- Bootstrap seed is a hash of candidate/stage/price-source/scenario (`evaluator.py` `bootstrap_seed`) → reproducible evaluation (Spec M1 "same input, same result").
- Trial accounting: invalid formulations don't spend a trial; duplicates/near-duplicates and >2 per family rejected pre-evaluation; every admitted evaluation, including crashes, spends one trial (design doc same section). → Spec §8 "record total attempts".
- Ledger: gross trade ledger validated (chronological, finite economics, `gross_pnl == settlement − debit`), costs applied once downstream (`research/v3/ledger.py` `GrossTradeRow.validate`; design doc "Modeled evaluator gates"). → separates trusted accounting from strategy.
- Code-candidate loop (`research/lab/loop.py`): `ResearchLoop` persists `state.json`/runs/admissions files; `run_once` refuses when `complete`/`paused`/`failed`, increments `run_count`, and marks budget exhausted past `policy.max_attempts` (lines 168-200); up to `MAX_PROPOSAL_ATTEMPTS = 3` formulation attempts per run, duplicates screened via `_evaluated_semantic_hashes` (lines 800-812); `run_until_complete` loops until accepted or budget, escalating proposer temperature after admission failures (480-503); `pause`/`resume` exist (148-166); a `shutdown-report.md` is written by `_write_shutdown_report` (902). Resumability here is file-state based, so an interrupted process restarts from the persisted run count. Acceptance there is a validator metric vs policy target (`_meets_target`, `_is_accepted`), not the staged v3 gate set; the two are separate code paths (v3 uses `campaign.py`).
- Runner/control: `research/autoresearch.py` runs one declared command with timeout/max-run budget from TOML, mutable paths must be under `research/`, strips broker/API-key env vars from the child (lines ~25-150: `LoopConfig`, `_validate_config`, `BROKER_ENV_KEYS`, `_research_environment` signature). Lifecycle `ready/running/complete/paused/failed`, "budget exhaustion is not success", `shutdown-report.md` on every stop (`LOOP.md` "Lifecycle").
- Evidence authority: findings are `research_only`, `execution_authorized: false` (design doc "Portable finding contract"). → Spec §8 "no profit guarantee".

## 3. RDA — research/development loop

Read: [README.md](https://raw.githubusercontent.com/microsoft/RD-Agent/main/README.md) (first ~14 KB), [docs/scens/quant_agent_fin.rst](https://raw.githubusercontent.com/microsoft/RD-Agent/main/docs/scens/quant_agent_fin.rst) (first 5 KB), and these sources (base `https://github.com/microsoft/RD-Agent/blob/main/`): `rdagent/components/workflow/rd_loop.py` (lines 1-260), `rdagent/app/qlib_rd_loop/quant.py` (1-140), `rdagent/core/proposal.py` (classes/signatures, lines 24-47, 96-121), `rdagent/scenarios/qlib/proposal/bandit.py` (1-40), `developer/factor_runner.py` and `developer/feedback.py` (grep excerpts only).

- R/D split is explicit in code: `RDLoop` wires `hypothesis_gen` → `hypothesis2experiment` → `coder` (Development) → `runner` → `summarizer`; steps `direct_exp_gen`, `coding`, `running`, `feedback`, `record` (`rd_loop.py` `RDLoop.__init__`, methods). README Introduction: "'R' for proposing new ideas and 'D' for implementing them".
- Typed objects: `Hypothesis` (hypothesis, reason, concise_* fields), `HypothesisFeedback` (reason, decision bool, observations, hypothesis_evaluation, new_hypothesis), `Trace` DAG of (experiment, feedback) with `get_sota_experiment` (`core/proposal.py`). `record` appends `(exp, feedback)` to the trace (`rd_loop.py` `record`). → maps to Spec §6.6 registry + §7 Keep/Reject/Branch.
- Quant specialization: `QuantRDLoop` has factor vs model branches chosen by `hypo.action in ["factor","model"]`, with `QuantTrace` and a bandit module whose `Metrics` hold IC, ICIR, rank-IC, ARR, IR, MDD, Sharpe (`quant.py` `direct_exp_gen`; `bandit.py` `Metrics`). Feedback prompts compare against SOTA using IC, annualised excess return with cost, max drawdown (`feedback.py` `IMPORTANT_METRICS`).
- Dedup: new factors with correlation ≥0.99 to SOTA are dropped (`factor_runner.py` `deduplicate_new_factors`, threshold `< 0.99`).
- Exceptions become a rejected feedback entry rather than ending the loop (`rd_loop.py` `feedback`: `decision=False`); `skip_loop_error` for empty factor/model (`quant.py`).
- Backtest setup in docs: Qlib, CSI300, fixed train/valid/test dates, TopkDropout, costs (`quant_agent_fin.rst` "Qlib Configuration").
- Not suitable as a dependency (Spec §3.3 agrees): README says Linux only, Docker, conda, embedding/JSON-mode LLM; scope is cross-sectional factors/models, not multi-asset ETF allocation. Borrow: typed Hypothesis/Feedback/Trace, "exception → rejected feedback", dedup, concise-context fields (Spec §7 "compact context").
- Completion pass (`rdagent/scenarios/qlib/proposal/quant_proposal.py` 1-80, `scenarios/qlib/experiment/quant_experiment.py` grep, `rdagent/utils/workflow/loop.py` grep):
  - Action selection (factor vs model) is configurable: `QUANT_PROP_SETTING.action_selection == "bandit"` uses `QuantTrace.controller` (`EnvController`) on the last experiment's metrics, with first action `"factor"`; `"llm"` asks the model with hypothesis/feedback history prompts (`quant_proposal.py` `prepare_context`).
  - `QlibQuantScenario` takes `train_start/end`, `valid_start/end`, `test_start/end` from settings (`quant_experiment.py` lines 49-54): three splits, fixed by config. I did not find a one-use lock on the test split in the files read — unlike AQR.
  - `LoopBase` (`utils/workflow/loop.py`) provides session resume: `session_folder = <trace_path>/__session__`, per-step `dump` via secure pickle, `loop_n`/`step_n` remaining counters, and `skip_loop_error` to continue after specified exceptions (lines 99-134, 182-185, 249-308). → analogous to Spec §7 "interrupt/resume" but via pickled sessions; PrajnaTrade's SQLite registry is a simpler fit.
  - Not read: `scenarios/qlib/experiment/prompts.yaml` and knowledge-base persistence; any claim on RD-Agent "knowledge accumulation" beyond `Trace.hist` and `concise_knowledge` fields is unsupported here.

## 4. Comparison against Spec requirements

| Spec requirement | autoresearch | AQR | RDA |
|---|---|---|---|
| Agent-written code (§6.2, 6.5) | edits `train.py` | `code` candidate in `program.md` loop; v3 is JSON-only | LLM-coded factors/models in workspace |
| Fixed trusted evaluator (§9) | `prepare.py` | validators + gate policy + hashed stages | Qlib runner/templates |
| Keep/rollback (§7) | git commit/reset | gate pass; budget pause | `decision` bool, SOTA in trace DAG |
| Persistent record (§6.6) | `results.tsv` | hash-chained ledger, shutdown report | log trace |
| Discovery/validation/holdout (§8) | none | yes, one-use holdout | static train/valid/test dates |
| Multiple-testing/trial count (§8) | none | trial ledger, Bonferroni alpha, dedup | dedup only (read portion) |
| Isolation (§9) | convention | declared forbidden imports/env stripping | Docker (README) |

My inference (not a source claim): PrajnaTrade MVP = autoresearch loop and file contract + AQR staged/gated validation and append-only record + RDA's Hypothesis/Feedback/Trace vocabulary; real isolation for LLM-written code must be added by PrajnaTrade (Spec §9 allows restricting scope if not available).
